## Financial safety principles that remain mandatory

1. Every posted journal entry group balances, but a balanced journal does not prove liquidity or profitability.
2. A vendor receivable is not refund cash. Customer refunds must not wait for vendor recovery where a refund is owed.
3. A complaint alone is not vendor debt. Recovery requires an authorised, evidence-based ruling and a contractual basis.
4. Verify gateway outcomes by provider references and reconciliation; screenshots are not proof of repayment.
5. Timeouts are uncertain outcomes, not proof of failure. Do not release reservations or retry transfers until reconciled.
6. Never mark a change verified based only on code inspection. Require tests, and use a staging/gateway sandbox for provider workflows.

## System-wide state-transition and idempotency audit (20 October 2026)

- Added [`docs/audit/STATE_TRANSITION_AND_IDEMPOTENCY_REGISTER.md`](STATE_TRANSITION_AND_IDEMPOTENCY_REGISTER.md) to inventory current enum states, required lifecycle states, event families, transition constraints, replay/timeout rules, and acceptance tests. It explicitly labels implementation gaps instead of treating policy documentation as proof.
- **Critical / OPEN:** this is an initial register, not yet proof that every writer is guarded. Must trace all status writers across controllers, services, observers, listeners, jobs, commands, webhooks, callbacks, admin UI and mobile APIs; add explicit transition guards and database uniqueness/inbox constraints where absent; test duplicate and concurrent delivery.
- **Confirmed architectural gap remains:** checkout still creates a single shop-scoped order; parent checkout + vendor child allocation is not implemented/verified. Do not claim multi-vendor checkout complete.
- **Idempotency invariant:** every gateway or financial side effect must have a stable unique operation identity and be applied once; timeouts stay uncertain until provider reconciliation. Duplicate events are no-ops against persisted outcomes; conflicting payloads are quarantined. This applies across payment, refund, cashback, settlement, payout, recovery, pickup/delivery handover and scheduled jobs.
- Register commit: `0cadbfbac64f4197e2955f07cea9b40607b80572`. CI for this documentation-only commit and the immediately preceding wallet-credit validation fix remains pending at time of recording.

- **New webhook-inbox audit finding (20 October 2026):** The original inbox migration does enforce a unique database index on `processed_webhook_events.event_id`, and the handler compares payload hashes, which are positive controls. However, existing tests prove signature rejection and payment-settlement idempotency, not the inbox's own duplicate/concurrent-claim/retry/conflicting-payload/stale-worker paths. The duplicate-key recovery catches `QueryException` inside the same DB transaction; verify this behaves correctly on every supported production database (notably databases that mark a transaction failed after a constraint violation). The stale-worker diagnostic was malformed and has been corrected to log the event ID and claimed attempt generation. Add dedicated inbox lifecycle and concurrent-delivery tests before marking this control verified. **Status: OPEN — test/transaction semantics verification required.**

- **Webhook stale-worker fencing scope (20 October 2026):** The handler's `updateProcessedEvent()` uses `id + attempts` compare-and-set, so a stale worker cannot overwrite a newer attempt's inbox status. This is not end-to-end fencing: the `charge.success` path can still call `settlePaystackOrder()` and dispatch an automatic late-payment refund; `refund.processed` can finalize a financial operation; `refund.failed` can fail an operation/release its reservation; and transfer event handlers can mutate payout state before the final inbox update. Callers generally ignore the compare-and-set boolean, and a one-time ownership check would still race with lease expiry. A safe fix must bind the claim generation to the same database transaction/row locks that protect each financial state transition, plus idempotent/unique operation keys for external gateway dispatch; refund/payout branches need the same treatment, not just charge settlement. The 60-second stale-claim takeover means a paused worker may overlap a newer attempt. **Status: OPEN — high-priority financial side-effect race; no code fix claimed.**
